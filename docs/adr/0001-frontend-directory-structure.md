# ADR 0001: フロントエンドのディレクトリ構成とアーキテクチャ

## ステータス
承認済み

## 日付
2025-12-30

## 背景
プロジェクトが単純なファイルリスト表示から、検索、Git連携、AI分析などの複雑な機能を持つアプリケーションへと成長するにあたり、デフォルトのディレクトリ構造ではメンテナンスが困難になります。以下の要件を満たす構造が必要です：
1. フロントエンドとバックエンドのコードを明確に分離すること。
2. 他の機能に影響を与えずに各機能をスケールアップできること。
3. 汎用的なUI要素やロジックの再利用を容易にすること。

## 意思決定

### 1. ルートレベルのリネーム
Tauri標準のディレクトリ構成を以下のように変更しました：
- `src` -> `frontend`: Web関連のすべてのコード（React, CSSなど）を格納。
- `src-tauri` -> `backend`: Rust関連のコードおよびTauriの設定ファイルを格納。

### 2. フィーチャーベースのフロントエンド構成
`frontend/` 内に「Feature-slice」アーキテクチャの概念を取り入れた構造を採用しました：
- **`features/`**: ドメインやビジネスロジック単位で整理。例: `file-manager`, `ai-assistant`。
  - 各機能フォルダは独自の `components/`, `hooks/`, `types/`, `store/` を持ちます。
- **`shared/`**: ドメインに依存しない、再利用可能な実装を格納。
  - `shared/components/ui/`: 汎用UIコンポーネント（例: Shadcn UI）。
  - `shared/hooks/`: 汎用的なカスタムフック。
  - `shared/lib/`: 横断的なユーティリティ（例: `cn` 関数、APIクライアント）。

### 3. 命名規則
- **ディレクトリ**: すべて小文字とハイフンを用いた `kebab-case` を使用します（例: `file-manager`）。これにより、OS間の互換性を確保し、コンポーネントファイル（PascalCase）との視覚的な区別を明確にします。
- **コンポーネント**: Reactコンポーネントのファイル名には `PascalCase` を使用します（例: `FileList.tsx`）。

### 4. パスエイリアス（Path Aliases）
深い相対パス（`../../`）を避けるため、エイリアスを設定しました：
- `@/*`: `frontend/` を指す。
- `@features/*`: `frontend/features/` を指す。
- `@shared/*`: `frontend/shared/` を指す。

## 影響

### 正の側面
- **コードの発見性向上**: 特定の機能に関連するロジックが1箇所にまとまっているため、探しやすくなります。
- **結合度の低減**: 機能が自己完結することを推奨し、循環参照のリスクを軽減します。
- **拡張性**: 新しい機能（Git管理など）を追加する際、`features/` 下に新しいフォルダを作るだけで済みます。
- **一貫性**: コードベース全体で命名規則とパスが統一されます。

### 負の側面
- **初期設定の複雑さ**: 多くの設定ファイル（`tauri.conf.json`, `vite.config.ts`, `tsconfig.json`）の更新が必要でした。
- **学習コスト**: 新しい開発者は `features` と `shared` の使い分けの基準を理解する必要があります。
